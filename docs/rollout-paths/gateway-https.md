# Rollout path: gateway injection with HTTPS loading

Use this rollout path when the gateway should supply the initial instructions centrally and the assistant should retrieve detailed policy only for matching work. Read the [shared content and overlay rules](../adapting-in-an-organization.md#define-the-shared-content) first. This is an implementation plan; the repository does not yet contain the remote adapter or policy loader.

## Deployment inputs

| Input | Decision needed |
| --- | --- |
| Clients and gateway | Supported clients, API formats, gateway product and version, and authenticated caller identity |
| Policy publication | Approved HTTPS host, immutable release paths, release trust mechanism, and content allowed at the model provider |
| Loader | Shell helper or remote tool, its execution location, network access, and credential mechanism |
| Release assignment | How the gateway and loader keep a caller's session on one approved release |
| Operations | Owners, request and content limits, retention of old releases, rollback, and optional verified cache |

Deliver the gateway adapter, versioned catalog and artifacts, schemas, loader, client and service configuration, and integration tests. Use the organization's real infrastructure values; the examples below are not deployment defaults.

```text
Reviewed release ──→ gateway: baseline + overlay + compact catalog
                 └→ policy host: versioned packs and blueprints

Assistant ── model request ──→ gateway injects initial content ──→ model
Assistant ── selected artifact ID ──→ loader ── HTTPS ──→ policy host
                                      └── verified content back to assistant
```

The gateway supplies the initial instructions on model requests. The assistant selects packs from the injected catalog and calls a tool to load their contents. No policy bundle needs to be installed on developer machines. Gateway injection does not install skills, provide tools, or grant network access.

## Publish the release and catalog

Generate the gateway block and hosted artifacts from the same reviewed release. Put each pack and blueprint at an immutable HTTPS URL and compute its digest from the exact published bytes. Publish and verify the artifacts before activating their catalog at the gateway. Keep releases available while sessions use them.

Inject a compact catalog with every applicable pack's ID, trigger, and pinned reference. Blueprint descriptors can live in the verified pack to save initial context. For example, this YAML fragment describes one remote pack; it is a proposed catalog format, not a configuration an assistant recognizes automatically:

```yaml
release: acme-sec-1.0.0
packs:
  - id: acme-authentication
    trigger: Login, SSO, sessions, tokens, or changes to user identity
    url: https://policy.acme.example/releases/acme-sec-1.0.0/packs/authentication.md
    version: 1.0.0
    sha256: "<64 lowercase hex characters generated by the release build>"
    max_bytes: 65536
    blueprints:
      - id: acme-spa
        url: https://policy.acme.example/releases/acme-sec-1.0.0/blueprints/spa/1.0.0.yaml
        version: 1.0.0
        sha256: "<64 lowercase hex characters generated by the release build>"
        max_bytes: 65536
```

Implement and validate the catalog schema; reject unreplaced placeholders. The release build and loader must agree on how a pack declares its ID and version. Every dependency needs a pinned descriptor, whether in this catalog or in a verified pack. Do not follow other links as policy dependencies. Cap the number of dependencies and reject cycles.

The expected digest must come from the approved gateway block or a verified parent artifact. Fetching both content and its expected hash from an unpinned page on the policy host defeats the check. HTTPS authenticates the connection; the pinned digest identifies the approved content.

## Provide the loading tool

Choose an implementation that the supported assistants can actually call:

| Loader | What you provide |
| --- | --- |
| Shell-based loader | A reviewed helper in the execution environment that downloads raw bytes, verifies them, and validates the document |
| Remote tool, for example MCP | An authenticated service that accepts an artifact ID, resolves it within the approved release, performs the checks, and returns the verified content |

The shell helper can use existing command-line tools; it needs the execution environment to reach the policy host. A remote loader needs that access from its server; the client needs access to the loader. Both need explicit tool configuration. A centrally hosted loader avoids distributing a helper to each machine, but adds a service to operate. An assistant-generated download command can demonstrate the flow; it is not a substitute for a reviewed loader in an organization rollout.

Give the loader a bounded contract. For example, `load_policy(release, artifact_id)` accepts only IDs from the caller's authorized release and returns the ID, version, digest, and full verified content. This is an interface to implement, not a built-in tool. Do not accept arbitrary model-supplied URLs or let a requested release bypass the caller's assigned policy. Register the tool and describe its use in the injected overlay.

The loader must:

1. Resolve the artifact through the approved catalog. Use HTTPS with certificate verification, an exact destination allow-list, and no redirects. Require a successful HTTP response. Configure private CAs through the supported trust store.
2. Enforce connection and total timeouts and a byte limit during reading, including decompressed content. Choose explicit rollout limits, for example 5 seconds to connect, 20 seconds total, and 64 KiB per artifact. Bound retries and total work per call.
3. Download once, compare SHA-256 before parsing or returning content, then validate that same byte sequence. Check the declared ID and version and, for YAML or JSON, the [full schema requirements in the shared guide](../adapting-in-an-organization.md#packs-catalog-and-blueprints). A plain `curl | sha256sum` computes a digest but neither compares it nor retains the checked body for reading.
4. Return the verified content without summarizing or silently truncating it. On failure, return a safe error identifying the artifact and failed check; never return partial policy as usable content.

Configure authentication separately for the gateway and policy loader or host. For protected content, authorize the caller for the requested artifacts. Keep credentials in the tool's credential mechanism, outside the prompt, catalog, URLs, and logs. An intranet address does not replace identity. Allow only policy content approved for disclosure to the selected model service.

A gateway URL alone does not configure this download path. For example, Claude Code's sandbox domain rules govern network access by its Bash tool separately from model routing. See [Claude Code sandboxing](https://code.claude.com/docs/en/sandboxing) and [gateway connection settings](https://code.claude.com/docs/en/llm-gateway-connect). Test from the actual client or remote execution environment, not only a developer's terminal.

Add a concrete instruction to the generated gateway overlay, using the actual tool name you deployed:

```markdown
Load selected packs with `load_policy(release, artifact_id)` using the release
and IDs in this injected catalog. Read each verified pack and load all its
required blueprints before affected work. Apply pack requirements and use
blueprint values under ACME-POLICY-001. If the tool is unavailable, a result
is incomplete, or any check fails, follow ACME-POLICY-002. Do not replace the
loader with a browser summary, a different URL, or remembered content.
```

## Configure injection and updates

Deploy the initial block as a verified artifact. Authenticate its manifest or expected digest through the release channel, load it before serving requests, and refuse activation if verification fails. Include the baseline text, overlay, catalog, release identity, and loader instructions. Set a size budget and reject a build that would truncate these instructions on a supported client. Do not send local import markers or paths that exist only on the gateway.

Implement injection for each supported client API format. Preserve existing instructions, tool definitions, tool results, streaming, and required protocol headers. Insert the organization text in the format's supported instruction field, not as a user message. Reject unsupported inference formats on routes that require this policy rather than silently forwarding them without it. Retry handling must avoid duplicate injection without trusting a client-supplied "already injected" flag.

For Claude Code's Anthropic Messages format, append a separate system block and leave the existing first block untouched. Merging into its attribution block can cause added text to be stripped upstream. Other API formats need their own adapter; this is not a universal ordering rule. See the [Claude Code gateway compatibility guide](https://code.claude.com/docs/en/llm-gateway-protocol).

Configure the client to use the gateway and give each developer their own authenticated access. Where gateway use is mandatory, manage the client configuration and permitted provider access; injection only covers requests that actually traverse that route. See [Claude Code gateway rollout](https://code.claude.com/docs/en/llm-gateway-rollout).

Keep one release per session. Associate the session with its authenticated caller and assigned release at the gateway, and make the loader use the same assignment. Do not let an arbitrary session ID select another caller's policy. Keep the block stable for that session. If the client cannot support this, activate releases only after affected sessions end and start fresh ones. Apply this to retries and delegated requests too.

A remote design can retain manifests, pinned dependencies, and rollback. Roll back by activating a previous approved gateway release with its matching catalog and artifacts for new sessions. An optional cache must recheck content against the pinned digest and preserve authorization boundaries. It must not fall back to a different release after a download failure. Without an approved cached copy, offline or unavailable content stops affected work.

## What the repository example covers

The [LiteLLM example](../../examples/organization-bundle/gateway/) checks a configured block's digest and appends it in `async_pre_call_hook`. LiteLLM documents that hook for [modifying requests before model calls](https://docs.litellm.ai/docs/proxy/call_hooks). Verify the request shape with the exact gateway and client versions you deploy.

The current builder generates that block from the local overlay, including local catalog references. It needs a remote adapter for this option. The example also leaves out the remote catalog, HTTPS loader, full blueprint schema validation, client provisioning, and session-to-release assignment. Its tests exercise the hook with a stubbed LiteLLM import; they are not an end-to-end gateway or model test.

## Acceptance checks

Run the common [verification cases](../adapting-in-an-organization.md#verify-before-rollout) through each actual client and gateway route. Also test unsupported inference formats, retries, streaming and tool calls, cross-caller artifact access, session identity reuse, release changes during a session, and any cache. Verify that a failed download returns no usable policy and that the assistant stops affected work. A loader unit test cannot establish that the assistant invokes it.
